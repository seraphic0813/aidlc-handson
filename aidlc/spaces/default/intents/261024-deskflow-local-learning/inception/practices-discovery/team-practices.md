# DeskFlow：開発・テスト・ローカル運用方針

> 本人の5問の回答を反映した方針。本工程の承認と共通方針への反映は、この文書を確認した後に行う。

## Way of Working

- 私たちは通常、現在のブランチで小さな変更単位として作業を進める。別のブランチが必要になった場合は、作成前に本人へ相談する。
- 作業内容・確認結果を説明して、本人の工程承認を待つ。実装前にはコード計画の承認を得る。
- コミット・プッシュ・マージは、明示的な依頼がある場合だけ行う。工程の承認自体を、これらのGit操作の依頼と読み替えない。
- 根拠：[本工程Q1：A](practices-discovery-questions.md)、本人が会話で提示したGlobal Codex Instructions、企画の引き継ぎ概要。

## Walking Skeleton

- 私たちは、画面から保存・再表示まで動く最小一貫版（walking skeleton）だけを先に作る独立した確認は設けない。
- 登録 → 担当・状況の更新 → 完了 → 過去の検索という、決めた業務の順序に沿って機能を実装・確認する。
- 最小一貫版の独立した確認を設けなくても、必要な設計・テスト、工程ごとの本人判断、実装前のコード計画承認は維持する。
- 根拠：[本工程Q2：B](practices-discovery-questions.md)、企画の対象範囲。選択はclassicの既定offとも一致する。

## Testing Posture

- **Methodology**: test-after
- **Methodology evidence**: 本工程Q3で本人がAを選び、各層を実装してからその層のテストを書いて実行する方法を選択した。
- **Ordering**: 私たちは各テスト可能な層を実装してから、その層のテストを書いて実行する。
- Test Strategyは承認済みのStandardを維持し、単体テストと主要な境界の結合テストを扱う。
- classicに適用される行カバレッジ80%以上の下限を維持する。目標を満たすために適切なテストを追加し、通過させるための目標引き下げは行わない。
- 統合前の自動検証と、構成に応じた整形・静的チェックを維持する。今回は独立したホスト型CI構築が対象外のため、ローカルで再実行できる検証コマンドを設計する。マージを実施する場合は、その前に必要な検証を通す。
- テストの具体的な道具・コマンド・対象コードは、技術構成と要件が決まってから定義する。既存のアプリ用テスト基盤があるとは扱わない。
- 根拠：[本工程Q3：A](practices-discovery-questions.md)、`aidlc/spaces/default/memory/org.md#Testing Posture`、選択中の計画・状態。

## Deployment

- 私たちは架空データを使うローカル演習だけを行う。AWSへのデプロイ、外部公開、実データの使用は行わない。
- 追加費用のかからない構成とする。必要な無料ソフトは目的と導入内容を説明したうえで追加できる。
- 再現可能な起動・停止・再起動の手順と、データ保存・復旧手順をローカル用に用意する。実装・テストの結果を説明し、本人の判断を待ってローカル起動・操作確認へ進む。
- ローカル操作は、AIが操作内容とコマンドを説明して実行し、本人が結果を確認する。
- 組織既定のステージング・本番への配備は、今回のローカル限定という明示条件には適用しない。
- 根拠：[本工程Q4：A](practices-discovery-questions.md)、企画の引き継ぎ概要、企画の回答Q1・Q2、承認済みの実行計画。

## Code Style

- 私たちは採用した言語の一般的な命名規則と、プロジェクトで確定する整形・静的チェック設定に従う。追加の独自規約は設けない。
- 既存の共通処理を優先し、目的に必要な最小限の変更にする。説明コメントは、既存規約がなければ日本語で設計意図を記す。
- 言語・フレームワーク・整形ツールをこの工程では選択しない。技術構成が決まった段階で、その構成に適した無料の道具と設定を具体化する。
- 根拠：[本工程Q5：A](practices-discovery-questions.md)、`aidlc/spaces/default/memory/org.md#Code Style`、本人が会話で提示したGlobal Codex Instructions。

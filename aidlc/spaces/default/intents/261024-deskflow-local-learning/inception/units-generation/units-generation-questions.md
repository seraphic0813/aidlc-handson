# DeskFlow：実装単位を決める質問

各質問の `[Answer]:` に選択肢の文字または希望を記入し、保存してください。
実装単位は、設計・実装・テストをまとめて進める範囲です。画面と業務処理の責任を分けることと、別々のアプリとして起動することは区別します。

## 引き継ぐ決定

- 論理的な責任はDeskFlowInterface（4画面）とInquiryManagement（問い合わせ管理）の2つ。問い合わせの正式な記録は後者だけが所有する。
- 架空データのみ、1人のローカル演習。AWSへのデプロイ・外部公開は行わない。
- 各工程と実装前のコード計画は本人が承認する。単位ごとに進め、並列実装はしない。最小版だけの独立した先行確認は設けない。
- 言語・フレームワーク・保存方式は後の設計で決める。この質問では導入や起動を行わない。

根拠：[コンポーネント](../domain-design/components.md)、[設計判断](../domain-design/decisions.md)、[要件](../requirements-analysis/requirements.md)。

## Q1. [設計担当] 画面と問い合わせ管理を、どの単位にまとめますか？

A. 1つのローカルWebアプリにまとめる（推奨）。U1 / `u1-deskflow` に両コンポーネントと全機能を含める。種類は `service`（起動できるアプリ）で、同じアプリが画面と業務処理を提供する。内部の責任分離は保ち、単位間の依存や連携契約は生じない。起動・停止・バックアップの説明をまとめやすい一方、画面だけを独立して配布する構成にはしない。

B. 画面と問い合わせ管理を別の起動単位にする。画面を `ui`、問い合わせ管理を `service` とし、画面が管理側に依存する。別々に変更・起動できる一方、起動手順と単位間の通信契約の設計が増える。選択時は、現在省略している契約設計を含め、計画への影響を相談する。

## Q2. [開発担当] アプリのコードを置く場所はどちらにしますか？

A. このワークスペースの `deskflow/` フォルダーにまとめる（推奨）。学習記録の `aidlc/` とアプリのコード・テスト・起動設定を見分けやすくする。実際のファイル構成は後のコード計画で承認する。

B. このワークスペースのルートに置く。アプリをルートから扱える一方、既存の学習記録や設定と同じ階層になる。実際のファイル構成は後のコード計画で承認する。

## 回答後の進め方

回答の曖昧さや矛盾を確認した後、単位数・境界・依存関係・種類をまとめた分割計画を提示し、承認を待つ。その承認後に実装単位の文書と要件対応表を作る。実行コードはこの工程では作らない。

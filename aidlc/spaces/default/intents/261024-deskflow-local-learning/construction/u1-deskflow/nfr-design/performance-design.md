# DeskFlow：性能・操作性の設計

- [性能・操作性の要件](../nfr-requirements/performance-requirements.md)：NFR1.1・NFR1.2、NFR4.1〜NFR4.3。
- [機能仕様](../functional-design/functional-spec.md)、[採用技術](../nfr-requirements/tech-stack-decisions.md)。

## P1：読取と表示の経路

NFR1.1・NFR1.2を実現する。Reactから同一オリジンの一覧操作を1回呼び、Nodeは同じSQLite読取トランザクションで正式な問い合わせを取得する。100件の検証範囲では5項目のUnicode比較・状態絞込・安定ソートを管理側で行い、総件数と対象20件を同じ結果集合から返す。受付番号の数値部分は文字列順にせず数値として比較する。

登録時刻と受付番号で順序を固定し、更新時刻で並び替えない。件数が小さい段階で別の検索インデックスや正規化済みの正本を増やさず、検索・一覧・詳細は同じ保存値を参照する。件数増加が依頼された場合は走査時間を測り直し、その時点で索引や検索方式を検討する。

## P2：キャッシュと待機の扱い

正確さを優先し、問い合わせAPIは保存のたびに無効化する独自キャッシュを持たず、応答にno-storeを付ける。Reactは表示中の値と入力を保持するが、一覧へ戻る・再読込・保存成功の際は正式データを取得する。取得結果には画面の要求番号を対応させ、最後の条件に対する応答だけを反映する。

通常系の2秒を、管理側取得・検証・保存0.5秒、画面反映0.5秒、通信と余裕1秒の診断目安に分ける。これは独立の保証値ではなく、最終判定は操作から表示までの実測値とする。SQLiteの接続は管理側で1本を所有し、短い同期処理を用いる。長い処理を同じイベントループに追加しない。DBロック待ち1秒、画面要求待ち10秒は障害時の上限であり、性能目標の緩和ではない。

## P3：ReactとAtomic Designの操作性

NFR4.1〜NFR4.3を実現する。atomsはHTMLのbutton・input・label等の意味を保持し、見えるフォーカスを共通CSSで提供する。moleculesは入力ラベルと説明・エラーの関連を管理し、organismsはフォームと一覧のまとまりを表現する。pagesが画面遷移と読み込み・競合・未保存を調整し、templatesは表示配置を担当する。

非同期保存結果は文字の通知領域へ反映し、入力不備ではエラー概要へフォーカスを移し、該当欄へ辿れるようにする。競合は入力と正式値を別領域で示す。無効状態を色だけで示さず、理由を文字で伝える。HTMLのテキスト折返しと可変幅レイアウトを用い、200%では詳細を内容→対応の縦並びへ変更する。

## P4：検証

性能計測用の独立した100件の保存先を使い、一覧・検索・登録・更新を各5回、1操作ずつ実行して個別値・最大値を記録する。開始は操作イベント、終了は結果の画面反映。登録と更新は各回の前に基準状態へ戻す。操作の結果が失敗した回は成功操作の性能値へ混ぜず、失敗として別記する。

React Testing Libraryでラベルから入力・操作を行い、処理中、入力保持、エラー、競合、正常0件を確認する。実ブラウザーでキーボード主要経路と200%拡大、上限長の表示を確認し、未実測の値を達成済みと記録しない。

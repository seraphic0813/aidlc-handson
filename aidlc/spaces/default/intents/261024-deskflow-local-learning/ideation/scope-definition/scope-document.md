# DeskFlow：最初の版の対象範囲

## 参照資料

- [目的と成功条件](../intent-capture/intent-statement.md)：利用者、成功条件S1〜S3、架空データ・ローカル限定の境界。
- [対象範囲の回答記録](scope-definition-questions.md)：本工程のQ1〜Q5。

## 目的と利用者

架空のIT窓口を題材に、過去の問い合わせと回答を見つけにくく、同じ調査を繰り返す問題を扱う。問い合わせをする社員本人が登録し、主な利用者である窓口担当者が対応する。窓口責任者の、対応漏れを把握したいという関心も考慮する。根拠：目的と成功条件、Q1・Q2。

## 初回に含める範囲

| 機能 | 初回で扱うこと | 対応する成功条件・根拠 |
|---|---|---|
| 問い合わせの登録 | 社員本人が架空のIT問い合わせを登録する | S2、Q1・Q2 |
| 担当・状況の把握と更新 | 窓口担当者が担当者と状況を確認・更新し、未対応のものを特定できる | S1・S2、Q3・Q4 |
| 対応完了と回答の記録 | 受付から対応完了まで進め、後で問い合わせと回答を確認できるようにする | S2・S3、Q3・Q4 |
| 過去の問い合わせと回答の検索 | 用意した過去の問い合わせから、目的の問い合わせと回答を見つける | S3、Q3・Q4 |

上記は機能の境界である。入力項目、検索条件、状態の種類、操作権限などの具体的な仕様は、後の要件整理・設計で決める。

## 初回に含めない範囲

| 項目 | 扱い | 根拠 |
|---|---|---|
| 実在アカウントによるログイン、社内認証基盤との接続 | 対象外 | 目的と成功条件、本工程Q1 |
| AWSへのデプロイ、外部公開 | 対象外 | 目的と成功条件 |
| 実在の問い合わせなどの実データ | 使用しない。架空データだけを使う | 目的と成功条件 |
| 添付ファイルの登録・ダウンロード | 初回には含めず、将来の検討候補とする | Q3 |
| 担当者別の件数集計 | 初回には含めず、将来の検討候補とする | Q3 |
| メール通知を模した画面内の通知 | 初回には含めず、将来の検討候補とする | Q3 |

将来の検討候補は実装を約束したものではない。

## 優先順位と機能の依存関係

初回は基本の3つの成功条件に集中し、その達成に必要な機能をMust Haveとする。添付ファイル・件数集計・模擬メール通知はWon't Have（初回）に分類する。今回、Should HaveやCould Haveの追加機能は設けない。根拠：Q3。

確認する順序は、登録 → 担当・状況の更新 → 完了 → 過去の検索とする。更新するには問い合わせが必要であり、過去の回答を探すには問い合わせと回答の記録が必要になる。この依存関係を踏まえ、業務の流れを優先する。根拠：Q1・Q4、目的と成功条件S2・S3。

機能候補と依存関係の一覧は、[優先順位付きの機能候補](intent-backlog.md)に記載する。

## 価値の流れ

| 順 | 利用者の行動 | 得られる価値 | 根拠 |
|---|---|---|---|
| 1 | 社員がITに関する問い合わせを登録する | 問い合わせを対応の入口に載せる | Q1・Q2、S2 |
| 2 | 窓口担当者が担当者と状況を確認・更新する | 未対応と担当者を把握できる | S1・S2、Q4 |
| 3 | 窓口担当者が対応を完了し、回答を残す | 受付から完了までを確認でき、回答が後から参照できる | S2・S3、Q4 |
| 4 | 窓口担当者が過去の問い合わせと回答を探す | 過去の対応を見つけ、同じ調査を繰り返す問題に対処する | S3、目的と成功条件の問題記述 |

## 初回の完了条件と期限

架空データを使い、次の3つを確認する。根拠：目的と成功条件S1〜S3。

- 用意した問い合わせについて、未対応のものと担当者を漏れなく特定できる。
- 1件の問い合わせが受付から対応完了まで進むことを確認できる。
- 用意した過去の問い合わせから、目的の問い合わせと回答を見つけられる。

期限は設けず、一工程ずつ確認しながら進める。ローカル起動とローカル運用も体験し、各承認点では体験者本人の判断を待つ。根拠：Q5、目的と成功条件の学習目的。
